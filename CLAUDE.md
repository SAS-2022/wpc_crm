## Decisions (do not re-research)
- Backend: Firebase — Auth (email/password), Firestore, Realtime Database (live locations only), Storage (attachments).
- Roles stored in `users/{uid}.role`: `sales_exec` | `kam` | `sales_manager` | `gm` | `hr` | `accounting` | `procurement` (last three added 2026-10-17, see "HR" below). Enforced in security rules via `get()` on the user doc.
- KAM supervises sales execs where `users.kamId == kam uid`. KAMs normally own no clients, but Odoo lists some clients under a KAM: KAMs have an Odoo name too and receive those clients (import + saving the user) until they move them to their team (user decision 2026-10-16, reverses "sales execs only").
- State: Riverpod. Routing: go_router (role-based redirects). Maps: google_maps_flutter (switched from flutter_map/OSM 2026-10-13 for better Saudi business coverage). Markers drawn as images by `MarkerIcons` in `core/map_controls.dart`. On web, wrap every widget drawn over a GoogleMap (buttons, cards, sheets) in `PointerInterceptor` (pointer_interceptor), or clicks also reach the map (double-click on "+" zoomed to the click point). API keys: Android `MAPS_API_KEY` in `android/local.properties`, iOS `GMSApiKey` in `ios/Runner/Info.plist`, web script tag in `web/index.html` (one restricted key per platform). The web key is restricted to port 5050: run the web app locally with `flutter run -d chrome --web-port 5050` (other ports get Maps errors). Add the hosting domain (`wpc-crm-a9247.web.app`) to the key's allowed referrers before using the deployed dashboard.
- Location: geolocator with Android foreground service + iOS "Always". Tracking only during work hours (user decision 2026-10-14, replaces 24/7): default Saturday–Thursday 08:00–17:00 Saudi time (UTC+3; end changed from 18:00 on 2026-10-16, Friday off; the default lives in `WorkHours.defaults` and `DEFAULT_WORK_HOURS` in functions/index.js — keep both and web/privacy.html + support.html in sync), editable by GM/manager at More → Work hours, stored in RTDB `settings/workHours` {days[weekday 1–7], start, end (minutes)}; logic in `tracking/work_hours.dart` (unit tested). Off duty the tracker sends nothing (no positions, no GPS/permission heartbeat), removes `live_locations/{uid}`, sets `presence.onDuty=false` (live map: "Off duty"), the Android service notification says "Off duty – your location is not shared", and it keeps a low-power coarse stream only so iOS doesn't suspend the app. No tracking notification or log entry is created outside work hours (checked on the server clock too; user decision 2026-10-16). Route history is deleted after 90 days by the scheduled `cleanRouteHistory` function (03:00 Riyadh). Send location every 2 minutes to RTDB (user decision; team is 7 now, max ~11). Keep RTDB (user decision) and use it for honest live data: onDisconnect presence (online/offline), updatedAt + accuracy shown on the live map, and flag mocked GPS (geolocator `Position.isMocked`).
- Client import: Excel/CSV parsed client-side on web dashboard, match by Tax ID (VAT), else normalized name; same-VAT rows merge into one client (other names kept as `aliases`). Preview diff before commit. Contacts without coordinates are imported too (lat/lng null, grey, "No location") and appear on the map once a location is set in-app or a later import resolves their pin. Logic in `lib/features/import/` (unit tested). Second importer `/import/locations`: sheet of name (or Tax ID) + location (link, "lat, lng" text, or Latitude/Longitude columns) updates locations of existing clients only; matches name or aliases; fills missing locations unless "replace existing" is ticked. Optional "add unmatched rows as new clients" (one per name; AREA column → city; pivot header salesperson → assignedTo via odooName; category B).
- Marker colour (`features/clients/visit_rules.dart`): client `category` A/B/C (default B) + days since last visit → green/yellow/red; never visited = red. Thresholds in Firestore `settings/visitRules` (defaults A 7/14, B 14/28, C 30/45), edited by GM/manager at More → Visit frequency. Blue = on today's plan (approved, not done). Markers show the category letter. ## Odoo export (Contact (res.partner).xlsx, ~2,540 rows)
Columns: Company Name, Complete Name, Is a Company, Google Pin, Total Payable, Total Receivable, Currency, Account Receivable, Account Payable, Contact Address Complete, Mobile, Activities, City, Tags, Company.
- Location is only a `Google Pin` short link (maps.app.goo.gl, ~606 rows). It redirects to a URL containing `!3d<lat>!4d<lng>` (use these, not the `@` viewport). Browsers can't follow it (CORS): on phones the app follows the redirects itself (`import_service._resolveOnDevice`); only the web dashboard needs the `resolvePins` Cloud Function.
- Export also has Phone, Salesperson, Street, State, Country, Tax ID. Odoo has no exportable ID; Tax ID is the key (~60% of pinned rows have one).
- Pin formats: maps.app.goo.gl / goo.gl / share.google short links (need `resolvePins` Cloud Function in `functions/`), or full URLs with coords (parsed in app). share.google links lead to a search page and can't be resolved.
- Salesperson → app user via `users.odooName` (exact Odoo text, e.g. "Sami Mansour @ Sales"); active sales execs and KAMs (`uidBySalesperson` in `import_plan.dart`) — manager rows stay unassigned. The client list/map salesperson filter lists every active sales exec and KAM plus anyone else who owns clients. Import only fills an empty assignment. Saving a sales exec with an odooName also assigns their unassigned clients (`UsersRepository._assignOdooClients`).
- Odoo webhook / API connection: ON HOLD until management approves. Do not connect to Odoo. A webhook (Odoo automation rule → Cloud Function) is the planned live-sync path; its payload includes the record id.
- Rows with empty Company Name and Is a Company = 1 are companies; child contacts have Company Name set.
- Odoo API research (2026-10-16, still ON HOLD): use the JSON-2 API (`POST /json/2/<model>/<method>`, `Authorization: bearer <key>`); XML-RPC/JSON-RPC are deprecated (removed in Odoo Online 21.1 / Odoo 22). On Odoo Online the external API needs the Custom plan (Odoo.sh / self-hosted: no gate). Keys last at most 3 months (rotate; keep in Firebase Secret Manager, call only from Cloud Functions). Odoo Cloud acceptable use ≈ 1 call/s, no parallel calls: batch `search_read`, use webhooks (automation rule → "Send Webhook Notification" → Cloud Function) instead of polling. Use a dedicated read-only bot user. Key by `res.partner.id` once connected (replaces VAT/name matching). Needed from the user: hosting type + version, plan, bot user + API key, DB name/URL, technical names of custom fields (Google Pin is likely `x_studio_…`).

## Clients editing
Sales execs edit name/contact/address/location/notes of their own clients and add clients for themselves (`source: 'manual'`, duplicate warning by name/alias/VAT); category & assignment are KAM/manager only. Odoo import also stores Company Name (as legalName), Street, State, Country, Total Receivable/Payable, Currency, and optional "Email"/"Contact Person" columns (placeholders like ".", "Contact" or phone numbers are dropped, `cleanContactPerson`), "Is a Company" → `clientType` 'company'|'individual' (empty cell = unset) and "Company ID" (CR number) → `companyId` (2026-10-17). Company / Individual is a filter (`clientTypeFilterProvider`); type and Company ID are edited by supervisors like VAT. Import screen switch "Only fill missing fields" (`buildPlan(fillOnly: true)`, `fillChanges`): matched existing clients get only contact person / client type / company ID where empty — no new clients, no assignment, location or hidden changes. Odoo child contacts ("Parent, Person", Is a Company = false) attach to the parent as `contacts` [{name, phone, mobile}] instead of becoming clients. Excel gives booleans as "true"/"false".

Client locations (2026-10-17): a client can have several labelled locations (office, factory, showroom, …). `lat`/`lng` stay the MAIN location (imports, duplicates, plans, plan map, "No location" use only it) labelled by `mainLocationType`; more in `extraLocations` [{id, typeId, lat, lng, address}] (only shown while a main exists). `Client.locations` = main + extras; `locationsUpdate(list)` saves a whole list (first = main; "Make main" reorders); `nearestLocation`, `metersBetween` (all in `client.dart`, unit tested). Labels: editable list `settings/locationTypes` (same shape and editor as client tags: `TagList.locationTypes`, `ClientTagsScreen(kind:)`, More → Location types, `/location-types`, GM / SM; defaults Office, Factory, Showroom, Warehouse, Workshop, Branch). Client page lists locations (add / edit `ClientLocationEditor` / make main / delete; whoever may edit the client, incl. the sales exec for own clients — rules allow `mainLocationType`, `extraLocations`); Directions asks which location when several. Map: one pin per location in the client's colour (user decision: a visit to any location turns the whole client green). Check-in picks the location nearest the phone (dropdown to change), measures distance to it and saves `locationId` + `locationTypeId` on the visit (shown as "Client · Factory"). Merge keeps all locations (within 30 m = one). Edit screen: main label dropdown, plus "Other locations" (`ClientLocationsList(extrasOnly: true)`, saved right away; existing clients with a main location only) — added because the user looked for "Add location" there; clearing main coordinates promotes the first extra.

Client tags (2026-10-17, `features/clients/client_tags.dart`, unit tested): business tags (defaults Factory, Workshop, Contractor, Interior Designer, Showroom, EN + AR) in Firestore `settings/clientTags` {tags: [{id, en, ar}]} (defaults used until first save); GM / sales manager add, rename, delete at More → Client tags (`/client-tags`; names unique ignoring case, spaces, punctuation, Arabic letter forms — checked in a transaction; delete also removes the id from clients). Clients hold `tagIds` (several allowed); KAM / managers set them on the edit screen or in bulk from the Clients list selection (tag icon: add / remove, `setTagsMany`). Filters (2026-10-17, `client_filters.dart`): Clients list and map share one "Filters" button (badge = active count) opening a sheet with Salesperson (supervisors), Type (Company / Individual) and Tags (any of the selected); active filters show as removable chips with "Clear all". Status chips (list) / legend chips (map), Hidden and Possible duplicates stay inline. All filter providers are applied in `filteredClientsProvider`.

Excel export (2026-10-17, web only, supervisors): Clients list download icon exports the current list (search, status chip, filters, hidden view) or, in selection mode, the ticked clients. A dialog of checkboxes picks the columns (`ExportField` in `features/clients/client_export.dart`, unit tested; choice remembered per browser in shared_preferences); headers in the UI language, RTL sheet in Arabic. Download via `core/save_file.dart` (package:web on web, stub elsewhere).

Hidden clients (2026-10-14): KAM / sales manager / GM hide a client from its page (eye icon; for clients that belong to no salesperson). `allClientsProvider` = everything readable (client page, imports, duplicate checks, plan/route lookups); `clientsProvider` = hidden left out (lists, map, plan add sheet, statistics). Visits and plan items of hidden clients are dropped from Home stats, Reports, the Visits list and route history via `hiddenClientIdsProvider`; existing plan items stay in plans. Bulk: Clients list → checklist icon (or long-press) selects clients → Hide / Show again (`setHiddenMany`, batched). A "Hidden clients (n)" chip in the Clients list shows hidden ones; it appears only for supervisors and only when some are hidden. Imports never change `hidden`; `_assignOdooClients` skips hidden clients. No rules change needed (supervisors may update any client field).

Delete client (2026-10-17): GM / sales manager, trash icon on the client page (`ClientsRepository.delete`): deletes the client, its plan items and its attachment docs + files; its visits are KEPT (user decision; reports/targets unchanged, visit detail hides "Open client"). If the client has visits (`visitCount`, count query) the dialog requires the user's own login password (`reauthenticateWithCredential`) — app-side only, the rules just require isAdmin. A deleted client still in Odoo comes back as a new client on the next Odoo import (not blocked like `mergedFrom`).

Possible duplicates (2026-10-15): Clients list chip "Possible duplicates (n)" (supervisors, only when some) shows groups (`features/clients/duplicates.dart`, unit tested): same Tax ID, same name/alias (punctuation, spaces, Arabic letter forms, company words ignored), same phone (last 9 digits; a number on >3 clients is ignored), similar names (word subset / 75% words / ≤2 typos), or within 50 m sharing a name word; different Tax IDs only group on identical names. Per group: hide a client, "Not duplicates" (`notDuplicates` ids on each client, any supervisor), "Merge" (sales manager / GM, since it edits visits and deletes clients): pick the client to keep; `ClientsRepository.merge` moves visits, plan items and attachment docs (files stay, download links work), fills empty fields, adds names as aliases, logs `mergedFrom` [{id, name, nameKey, vat, byId, at}] and deletes the others (`merge.dart`). The Odoo import skips rows matching a `mergedFrom` entry and keeps those names in aliases, so merged clients don't come back.

Client transfers (2026-10-15): move clients between sales execs from the client page (swap icon), the Clients list selection (swap icon) or the edit screen's Sales executive field, or (web only) the clients map pin sheet's "Move to another salesperson" — all go through `ClientsRepository.transfer`. GM / sales manager: any client to any active exec or Unassigned; KAM: only their own clients or their team's, to their team (app-side, `features/clients/transfer.dart`, unit tested; rules unchanged). A transfer appends {fromId, toId, byId, at} to `clients.transfers` (shown as "Transfer history" on the client page), deletes the previous owner's not-done plan items for those clients dated today or later (past plans and visits stay), and notifies both people (`clientsTransferredIn` / `clientsTransferredOut`, where `ownerId` = the other exec).

Phone calls (2026-10-17): a call is a visit doc with `type: 'call'` (old docs without `type` are visits), logged at `/clients/:id/call` (`AddVisitScreen(call: true)`: notes + attachments, no GPS, works on web) from the client page ("Log call"), the map pin sheet, plan items / Home today's plan (phone button next to "Add visit") and the Visits list (small FAB). User decisions: a call turns the client green (`lastVisitAt`) and ticks today's plan item like a visit; calls count toward the monthly target but are shown apart in purple (`callColor`, `visits/call_chip.dart`): "190 + 30 / 240" on Home tile, target bars, progress line and the Reports "Visits + calls" column (pace uses the total). Calls are never flagged, have no KAM "I was there", and are left off route history. Not required to be dialled from the app (the client may call in), but when the user taps a number on the client page (`appCallProvider`, `visits/app_calls.dart`, unit tested) the app remembers the start and, once the user comes back to the app (after it was really backgrounded), offers "Log it?"; the call is then saved with `callFromApp: true`, `callSeconds` (time away from the app — phones can't tell an app whether the call was answered) and `callStartedAt`; offered for 2 h, user can remove it ("Not this call"). Call recording: not built (iOS forbids it, Android/Play blocks it; legal consent issues — discussed with the user 2026-10-17).

## Rules and setup
- `firestore.rules`, `database.rules.json`, `storage.rules`. RTDB rules read roles from RTDB `roles/{uid}`, mirrored by `UsersRepository._save`.
- New users are created by admins in-app via a secondary FirebaseApp. The first GM is bootstrapped by hand in the console.
- App updates (2026-10-16, `features/app_update/app_update.dart`): Android asks Google Play (in_app_update, In-App Updates API) at start and on every resume; when a newer build is published it runs Play's immediate (full-screen) update, and if the user cancels, `UpdateGate` (in `MaterialApp.builder`) blocks the app with "Update required" until they update. No build numbers to set by hand (user decision). Works only for installs from Play (internal testing track too), not debug runs or sideloaded APKs. iOS: no in-app check — personal developer account, distributed via TestFlight, which updates automatically. Web: nothing (each deploy is live on reload).
- Profile (`/profile`, `features/users/profile_screen.dart`, from the name row in More): every user edits their own name and phone (rules allow self-update of only those keys), changes their password (re-authenticates with the current one) or emails themselves a reset link. Email, role, KAM and target stay admin-only. Login screen has "Forgot password?" (same message whether or not the email has an account).

- `settings/visitRules`: {A|B|C: {green, yellow}}
- `import_batches/{id}`: fileName, importedBy, added, updated, unchanged, skipped, createdAt
