## Decisions (do not re-research)
- Backend: Firebase — Auth (email/password), Firestore, Realtime Database (live locations only), Storage (attachments).
- Roles stored in `users/{uid}.role`: `sales_exec` | `kam` | `sales_manager` | `gm` | `hr` | `accounting` | `procurement` (last three added 2026-10-17, see "HR" below). Enforced in security rules via `get()` on the user doc.
- KAM supervises sales execs where `users.kamId == kam uid`. KAMs normally own no clients, but Odoo lists some clients under a KAM: KAMs have an Odoo name too and receive those clients (import + saving the user) until they move them to their team (user decision 2026-10-16, reverses "sales execs only").
- State: Riverpod. Routing: go_router (role-based redirects). Maps: google_maps_flutter (switched from flutter_map/OSM 2026-10-13 for better Saudi business coverage). Markers drawn as images by `MarkerIcons` in `core/map_controls.dart`. On web, wrap every widget drawn over a GoogleMap (buttons, cards, sheets) in `PointerInterceptor` (pointer_interceptor), or clicks also reach the map (double-click on "+" zoomed to the click point). API keys: Android `MAPS_API_KEY` in `android/local.properties`, iOS `GMSApiKey` in `ios/Runner/Info.plist`, web script tag in `web/index.html` (one restricted key per platform). The web key is restricted to port 5050: run the web app locally with `flutter run -d chrome --web-port 5050` (other ports get Maps errors). Add the hosting domain (`wpc-crm-a9247.web.app`) to the key's allowed referrers before using the deployed dashboard.
- Location: geolocator with Android foreground service + iOS "Always". Tracking only during work hours (user decision 2026-10-14, replaces 24/7): default Saturday–Thursday 08:00–17:00 Saudi time (UTC+3; end changed from 18:00 on 2026-10-16, Friday off; the default lives in `WorkHours.defaults` and `DEFAULT_WORK_HOURS` in functions/index.js — keep both and web/privacy.html + support.html in sync), editable by GM/manager at More → Work hours, stored in RTDB `settings/workHours` {days[weekday 1–7], start, end (minutes)}; logic in `tracking/work_hours.dart` (unit tested). Off duty the tracker sends nothing (no positions, no GPS/permission heartbeat), removes `live_locations/{uid}`, sets `presence.onDuty=false` (live map: "Off duty"), the Android service notification says "Off duty – your location is not shared", and it keeps a low-power coarse stream only so iOS doesn't suspend the app. No tracking notification or log entry is created outside work hours (checked on the server clock too; user decision 2026-10-16). Route history is deleted after 90 days by the scheduled `cleanRouteHistory` function (03:00 Riyadh). Send location every 30 seconds to RTDB (user decision 2026-10-18, testing on the new build; was 2 min; team is 7 now, max ~11); the presence heartbeat stays at 2 min (`heartbeatInterval`, each presence write runs `trackingAlerts`) and `snapRoute` routes only between fixes ≥100 s apart (`ROUTE_MIN_GAP_MS`) so Routes API cost stays as before; web/privacy.html says 30 seconds. One phone per account (2026-10-18, after a manager opened Ali's account in Riyadh while Ali tracked in Dammam and both phones' points mixed on 17 Oct — 34 stray points deleted, backup in that session's scratchpad): RTDB `tracking_device/{uid}` {id, platform, since}; install id in shared_preferences `trackingDeviceId` (`tracking/tracking_device.dart`); `LocationTracker` sends (positions, history, presence) only while its id is the owner, first phone claims, others stay silent (Android notification "Not sharing – … another phone") and Home `TrackingCard` shows "Your location is shared from another phone" + "Use this phone" (claims; e.g. new phone or reinstall). History points carry `d` (device id). Safety net: `mainTrack` (report.dart, same in functions `mainTrack` used by snapRoute; unit tested) keeps the main continuous track (≤200 km/h or ≤5 km between points — offline-queued points share one server time; rough fixes >100 m ignored) plus non-overlapping later tracks of 5+ points; Route history shows "n points from another phone ignored". Keep RTDB (user decision) and use it for honest live data: onDisconnect presence (online/offline), updatedAt + accuracy shown on the live map, and flag mocked GPS (geolocator `Position.isMocked`).
- Client import: Excel/CSV parsed client-side on web dashboard, match by Tax ID (VAT), else normalized name; same-VAT rows merge into one client (other names kept as `aliases`). Preview diff before commit. Contacts without coordinates are imported too (lat/lng null, grey, "No location") and appear on the map once a location is set in-app or a later import resolves their pin. Logic in `lib/features/import/` (unit tested). Second importer `/import/locations`: sheet of name (or Tax ID) + location (link, "lat, lng" text, or Latitude/Longitude columns) updates locations of existing clients only; matches name or aliases; fills missing locations unless "replace existing" is ticked. Optional "add unmatched rows as new clients" (one per name; AREA column → city; pivot header salesperson → assignedTo via odooName; category B).
- Marker colour (`features/clients/visit_rules.dart`): client `category` A/B/C (default B) + days since last visit → green/yellow/red; never visited = red. Thresholds in Firestore `settings/visitRules` (defaults A 7/14, B 14/28, C 30/45), edited by GM/manager at More → Visit frequency. Blue = on today's plan (approved, not done). Markers show the category letter. Salespeople have a colour + initials (`features/clients/person_style.dart`, palette avoids the status colours; slot from a hash of the uid, unit tested): KAM/managers see an initials badge on each client row, and the map has "Colour by: Visit status | Salesperson" (salesperson mode: pins in the person's colour with their initials instead of the category letter, legend chips that filter by person). ## Odoo export (Contact (res.partner).xlsx, ~2,540 rows)
Columns: Company Name, Complete Name, Is a Company, Google Pin, Total Payable, Total Receivable, Currency, Account Receivable, Account Payable, Contact Address Complete, Mobile, Activities, City, Tags, Company.
- Location is only a `Google Pin` short link (maps.app.goo.gl, ~606 rows). It redirects to a URL containing `!3d<lat>!4d<lng>` (use these, not the `@` viewport). Browsers can't follow it (CORS): on phones the app follows the redirects itself (`import_service._resolveOnDevice`); only the web dashboard needs the `resolvePins` Cloud Function.
- Export also has Phone, Salesperson, Street, State, Country, Tax ID. Odoo has no exportable ID; Tax ID is the key (~60% of pinned rows have one).
- Pin formats: maps.app.goo.gl / goo.gl / share.google short links (need `resolvePins` Cloud Function in `functions/`), or full URLs with coords (parsed in app). share.google links lead to a search page and can't be resolved. Some maps.app.goo.gl links (iPhone share sheet, `?g_st=ac`) redirect to a place URL with no coordinates, only a short Plus Code + address ("RH8W+2QH … الرياض") and a place id: read offline by `import/plus_code.dart` / `functions/plusCode.js` (keep in sync) — full codes decode alone, short codes use the Saudi city named last in the address as reference (city table in both files); no city → unreadable (place-id lookup would need the paid Places API).
- Salesperson → app user via `users.odooName` (exact Odoo text, e.g. "Sami Mansour @ Sales"); active sales execs and KAMs (`uidBySalesperson` in `import_plan.dart`) — manager rows stay unassigned. Saving a sales exec with an odooName also assigns their unassigned clients (`UsersRepository._assignOdooClients`).
- Two-way client sync plan (2026-10-22, accepted; waiting for the Odoo setup): `docs/odoo_client_sync_plan.md` (architecture, safeguards, open decisions, questions for the Odoo developers). ## Clients editing
Sales execs edit name/contact/address/location/notes of their own clients and add clients for themselves (`source: 'manual'`); VAT / CR are optional. Every new client from the app is checked by the `findClientDuplicates` Cloud Function (server-side because execs read only their own clients; rules in `functions/duplicates.js` = `duplicates.dart` + same CR number — keep in sync; `node --test` in functions/) → dialog `duplicate_check.dart`: only sales manager / GM may "Not a duplicate – add" (saves `notDuplicates` = the matched ids); others open / use an existing match or ask a manager (user decision 2026-10-18; app-side, rules unchanged). Plan add sheet: while searching, last row "Add \"<typed>\" as a new client" opens `ClientEditScreen(pickFor: owner)`, which returns the new (or picked existing) client id and selects it; category & assignment are KAM/manager only. Odoo import also stores Company Name (as legalName), Street, State, Country, Total Receivable/Payable, Currency, and optional "Email"/"Contact Person" columns (placeholders like ".", "Contact" or phone numbers are dropped, `cleanContactPerson`), "Is a Company" → `clientType` 'company'|'individual' (empty cell = unset) and "Company ID" (CR number) → `companyId` (2026-10-17). Company / Individual is a filter (`clientTypeFilterProvider`); type and Company ID are edited by supervisors like VAT. Import screen switch "Only fill missing fields" (`buildPlan(fillOnly: true)`, `fillChanges`): matched existing clients get only contact person / client type / company ID where empty — no new clients, no assignment, location or hidden changes. Odoo child contacts ("Parent, Person", Is a Company = false) attach to the parent as `contacts` [{name, phone, mobile}] instead of becoming clients. Excel gives booleans as "true"/"false".

Client locations (2026-10-17): a client can have several labelled locations (office, factory, showroom, …). `lat`/`lng` stay the MAIN location (imports, duplicates, plans, plan map, "No location" use only it) labelled by `mainLocationType`; more in `extraLocations` [{id, typeId, lat, lng, address}] (only shown while a main exists). `Client.locations` = main + extras; `locationsUpdate(list)` saves a whole list (first = main; "Make main" reorders); `nearestLocation`, `metersBetween` (all in `client.dart`, unit tested). Labels: editable list `settings/locationTypes` (same shape and editor as client tags: `TagList.locationTypes`, `ClientTagsScreen(kind:)`, More → Location types, `/location-types`, GM / SM; defaults Office, Factory, Showroom, Warehouse, Workshop, Branch). Client page lists locations (add / edit `ClientLocationEditor` / make main / delete; whoever may edit the client, incl. the sales exec for own clients — rules allow `mainLocationType`, `extraLocations`); Directions asks which location when several. Map: one pin per location in the client's colour (user decision: a visit to any location turns the whole client green). Check-in picks the location nearest the phone (dropdown to change), measures distance to it and saves `locationId` + `locationTypeId` on the visit (shown as "Client · Factory"). Merge keeps all locations (within 30 m = one). Edit screen: main label dropdown, plus "Other locations" (`ClientLocationsList(extrasOnly: true)`, saved right away; existing clients with a main location only) — added because the user looked for "Add location" there; clearing main coordinates promotes the first extra.

### B. Attendance: automatic check-in at a work location (phones), reports on the web
- Rule (user's spec): an employee is checked in when they come within 100 m of their work location; leaving doesn't check them out until the check-out time (default 17:00 = `WorkHours.end`, editable). After that time they are checked out on the first fix outside the radius. No fix at all after the check-out time → the nightly function closes the day at the last fix seen inside (`checkOutType: 'auto'`).
- Data: Firestore `work_sites/{id}` {name, lat, lng, radius (default 100), active} (HR / managers create them on the web by picking a point on the map); `users.workSiteIds` [] (an employee may have several, e.g. office + warehouse; empty = no attendance), `users.attendanceRequired`. Settings `settings/attendance` {checkOutAfter (minutes, default = work hours end), lateAfter (minutes), minAccuracy (default 50 m)}, maybe per-site overrides later. One doc per person per day: `attendance/{uid}_{yyyy-MM-dd}` {uid, date, month, siteId, checkInAt (server time), checkInLat/Lng, accuracy, mocked, checkOutAt, checkOutType: 'left'|'auto'|'manual'|'hr', exits [{at, backAt}] (left the site during the day, for HR only), editedBy?, editNote?}. A fixed doc id makes repeated writes harmless.
- Pure logic in `lib/features/attendance/attendance_rules.dart` (unit tested, like `work_hours.dart`): `decide(day state, fix, sites, settings, now) → none | checkIn | exit | backIn | checkOut`. Uses only fixes with accuracy ≤ minAccuracy; distance ≤ radius + small accuracy margin; never checks in on a non-work day; flags mocked GPS (stores it, doesn't block — same as visits).
- Phones: sales execs/KAMs already have the work-hours tracker (`location_tracker.dart`): call `decide` on each fix there. Untracked roles (HR, accounting, procurement, managers) must not be tracked all day (privacy): use the OS geofencing APIs instead (Android GeofencingClient / iOS region monitoring, which wake the app on enter/exit even when it's closed; pick a maintained plugin at build time, e.g. `native_geofence`) plus a one-shot GPS fix at the check-out time. Home gets an Attendance card: status, check-in time, and a "Check in now" button as a fallback when the automatic check-in didn't happen (it takes a fresh GPS fix and still requires being within the radius). Permission: "Always" location is needed for automatic check-in; explain this in the app and update `web/privacy.html` + `support.html` (the location is used only around work sites; nothing is tracked outside the sites).
- Server: rules let a user create/update only their own `attendance/{uid}_{today}` with `checkInAt == request.time` (no back-dating) and only add `checkOutAt`/`exits`; HR / GM may correct any day (with `editedBy` + `editNote`). A scheduled function `closeAttendance` (23:30 Riyadh) closes open days; optional `attendanceAlerts` tells HR who hasn't checked in by `lateAfter` (OPEN QUESTION: notify or report only? The user so far prefers few notifications).
- Web (HR, sales manager, GM; KAM for their team): `/attendance` day view (who is in / late / absent / on leave from C), month grid per person (check-in/out times, hours, late count, absences), CSV export, HR edit dialog. `/work-sites` page with a map to place sites and assign people.
- Test: unit tests for `decide` (enter, jitter at the edge, leave before vs after the check-out time, rough fixes, non-work day, several sites) and for the month summary; Android emulator (Extended controls → Location → route/GPX playback walking in and out of a 100 m circle) and iOS simulator (Features → Location → custom location / GPX); rules tests (no back-dating, no editing others); one full field day on a real phone (Xiaomi too, because of battery saving) before turning it on for everyone.

### C. Leave (vacation) management — web only (HR)
- Scope: a general employee-requests module, not only vacations: request types include annual leave, sick leave (attachment), emergency leave, unpaid leave and non-leave requests (e.g. salary certificate, letter, advance) that have no day count. Leave types consume a balance; other request types just have a status and HR's reply/attachment. HR area (HR, GM, sales manager) handles all of them.
- Data: `settings/leaveTypes` [{id: annual|sick|unpaid|emergency|…, name EN/AR, paid, needsAttachment}]; `settings/holidays` {yyyy: ['yyyy-MM-dd', …]} entered by HR (Saudi public holidays, Eid dates change every year). `leave_balances/{uid}_{year}` {uid, year, entitled {typeId: days}, carriedOver, adjustments [{days, typeId, note, byId, at}]} set by HR. `leave_requests/{id}` {uid, typeId, from, to ('yyyy-MM-dd'), halfDay?, days (computed), reason, attachment (Storage, e.g. sick note), status pending|approved|rejected|cancelled, decidedBy, decidedAt, comment, createdAt}.
- Used days are not stored as a counter: they're summed from approved requests of the year (pure function `leave_rules.dart`, unit tested: work days only, using `WorkHours.days`, so Friday doesn't count; holidays don't count; half days; requests across a year boundary split by year). Remaining = entitled + carriedOver + adjustments − used − pending (pending shown separately).
- Flow: employee asks on the web ("My leave": balance per type, request form showing the days the request would use, history, cancel while pending) → HR approves/rejects (OPEN QUESTION: should the KAM / sales manager approve first, then HR?) → notifications `leaveRequested` / `leaveApproved` / `leaveRejected` through the existing `notifications` + `sendPush` (add EN/AR texts there and in the ARB files). Approved leave shows on the attendance day view (B) as "On leave", not "Absent", and on Team plans.
- HR web pages: `/leave` requests queue (filters by status/type/person), balances table per year (edit entitlement, adjust with a note), team calendar (who is off when, clashes), CSV export. Saudi labour law gives 21 days a year (30 after 5 years of service) — HR enters the numbers; the app doesn't apply the law itself.
- Rules: employee reads own balance and requests, creates own `pending` requests and may only set `status: cancelled` on their own pending ones; HR and GM read/write all; others none (managers maybe read their team: OPEN QUESTION).
- Test: unit tests for day counting and balances; rules tests (employee can't approve or change days/entitlement, can't read others); web run at port 5050 with an HR and an employee test account.
